# desktop

Unfold's Electron shell, in TypeScript. It holds no graph logic: it manages windows and the operating
system's dialogs, and routes messages between windows and the Rust engine
([architecture §4](../docs/architecture.md#4-system-overview), [§13](../docs/architecture.md#13-security-and-privacy)).

## Processes

| Process | Source | Does |
| --- | --- | --- |
| Main | `src/main/` | Lifecycle, the single-instance lock, windows, the menu, dialogs, the `app://` protocol, hardening, and supervising the engine host |
| Engine host | `src/engine-host/` | A utility process. Loads the `unfold-node` addon (`crates/unfold-node`) and routes each window's port to it |
| Preload | `src/preload/` | Runs in each sandboxed window and exposes `window.unfold`, and nothing else |

Main process modules:

- `index.ts`: lifecycle. One copy per user (a second launch forwards its folder argument, which joins the workspace). At launch the saved windows come back. macOS keeps running with no windows; Windows and Linux quit with the last one. On quit, the engine host detaches every window (landing its board writes) and closes every live project before the app exits.
- `windows.ts`: the window factory (context isolation, sandbox, no Node, no webviews, no spellchecker; `hardenedPreferences`, which the render window starts from too) and the registry of windows. Each window has a numeric id and a stable key, and shows the whole workspace.
- `protocol.ts`, `app-url.ts`: the privileged `app://unfold/` scheme. It serves the built UI with a strict content security policy: no inline scripts or styles, no remote origins. In development, windows load the Vite dev server instead.
- `security.ts`: blocks navigation, `window.open`, webviews, downloads, and every permission request. Cancels any request that would leave the machine, and checks the sender frame of every IPC message.
- `menu.ts`: the app menu. Add Project… (the folder picker, then the folder joins the workspace) and New Window run in the main process. Every other item, Edit > Undo and Redo included, is forwarded to the focused window as a `menu_command` event.
- `dialogs.ts`: the folder picker, the export save dialog (Mermaid or PNG), the Remove Project confirmation, and the confirmation an agent's `add_project` needs. Paths outside a project come only from here, from a folder the person dropped on a window, or from the command line.
- `engine-host.ts`: forks the engine host and restarts it if it exits, with backoff. It gives up after more than five exits in a minute, and windows then show "unavailable". Each window gets its own `MessageChannelMain`. It also carries the main process's own trusted engine requests (`request`), the MCP server's untrusted ones (`untrusted`), and the engine events the main process follows (`onEvent`).
- `workspace.ts`: windows coming back, adding projects from the menu, the command line, the OS, or a drop, and remembering windows (see [Window restore](#window-restore)).
- `window-placement.ts`: reading saved windows and moving a restored window onto a visible screen.
- `export-name.ts`: the export dialog's default file name (`.mmd` or `.png`).
- `ipc.ts`: the window commands ([docs/ipc.md](../docs/ipc.md#window-commands-and-shell-events)), plus `add_dropped_folder`, which only the preload sends. The agent channel's commands go to the agent bridge.
- `agents/`: the agent bridge, the windows' view reports, links, and page revisions (see [The agent bridge](#the-agent-bridge)), and the render window that draws pages for images and checks (see [The render window](#the-render-window)).
- `mcp/`: the MCP server agents connect to, its tools, and what it teaches them (see [The MCP server](#the-mcp-server)).
- `app-paths.ts`: the app folders from architecture §8.2, the UI and addon locations, and parsing the folder from the command line.
- `updater.ts`, `update-policy.ts`: updates from GitHub Releases with electron-updater, the app's only network use (see [Packaging](#packaging)).

## Transport

The wire types live in `src/shared/transport.ts`. The `window.unfold` surface is in `src/shared/unfold-api.ts`, a types-only file the UI imports as `@unfold/desktop/unfold-api`.

```text
renderer (preload) ──MessagePort──▶ engine host ──dispatch/cancel──▶ addon (Rust)
        ▲                                │  ◀──sink(JSON)── events, stream messages
        └──── Electron IPC ──── main ────┘ (lifecycle only: init, attach, detach, shutdown)
```

- **Port protocol.** The renderer sends `{kind:"invoke", id, command, args}` and `{kind:"cancel", id}`. The host replies with `{kind:"result", id, ok, value|error}`, `{kind:"stream", id, message}`, and `{kind:"event", event}`. It also sends one `{kind:"status", state}` per attach, saying whether the addon is loaded.
- **Request ids.** The host gives every invoke a request id that is unique across all windows, because the addon's `cancel` takes only a request id. Stream messages are routed back by window id and request id, events by the event's `windows` list, and broadcasts (every project event) to every window.
- **Attach.** Every window shows the whole workspace, so attaching opens nothing: a window's commands dispatch at once. On detach, the host cancels the window's requests except closing writes (board and folder writes, the window's state and bounds), then calls `detachWindow`, which waits for those writes and releases the window's board claims and selection. Detaches of one window run in order. A reload only swaps the port.
- **No addon.** If the addon can't be loaded, the engine host logs why (`[engine-host] the engine addon could not be loaded from …`), every invoke is answered with `engine_unavailable`, and each window shows the "Reconnecting to the engine…" toast. The app never shows made-up data.
- **Trusted commands.** The commands that take an absolute path or manage windows ([docs/ipc.md](../docs/ipc.md#how-a-command-travels), `MAIN_PROCESS_ONLY` in `router.ts`) run only with `"trusted": true`, which only the main process's own requests get: main sends `{type:"request", id, windowId, command, args, trusted: true}` over the parent port, the engine host dispatches it with `trusted`, and answers `{type:"result", id, ok, value|error}`. A window's message naming one of these commands, or carrying a `trusted` field anywhere, is refused with `untrusted` before it reaches Rust; the router rebuilds every window command from `command` and `args`, so a window can't add the flag. The MCP server's requests for agents travel the same way with `trusted: false`, and the router treats them as a window's; one that sets `stream: true` (`search_text`) gets each stream message as `{type:"stream", id, message}` before its result.
- **Events for the main process.** The engine host also posts `{type:"event", event}` to the main process for the broadcasts it follows (`MAIN_EVENTS` in `transport.ts`: `preferences_changed`, so the MCP server starts or stops with Preferences › Agents).
- **Restarts.** If the engine host dies, each window is told, rejects its in-flight requests with `disconnected`, and shows the "Reconnecting to the engine…" toast. Once the engine host restarts, every window is attached again with a fresh port. Invokes made while no port is present are queued.
- **Shell events.** Some events come from the shell rather than from Rust, and arrive through `window.unfold.on` like engine events: `menu_command`, `board_state_transferred`, `focus_board`, `project_added`, `project_add_failed`, and the agent channel's `agent_edit`, `agent_read`, `agent_open_board`, `agent_create_board`, `agent_edit_board`, `agent_show`, `agent_repair`, `agent_finish`, and `agent_server_changed`, and the render window's `render_page` and `render_frame`.

The addon is loaded from `crates/unfold-node` in a checkout, and from `<resources>/unfold-node` when packaged: the engine host `require`s that directory, whose `package.json` points at the napi-rs loader `index.js`, which loads `unfold-node.<platform>.node` beside it (for example `unfold-node.darwin-arm64.node`).

## The engine addon

`crates/unfold-node` is a napi-rs v3 addon over `unfold_workspace::Host`, with no logic of its own. It exports exactly `init`, `subscribe`, `dispatch`, `cancel`, `detachWindow`, and `shutdown` ([docs/ipc.md](../docs/ipc.md#the-addons-surface-host)). Promises settle from Rust threads through thread-safe deferreds, so the JavaScript thread never waits. Sink messages and settlements share one ordered channel, a weak (unref'd) thread-safe function called without blocking, so a request settles only after its stream messages reached the sink; a panic rejects with `internal`. Build it with `just addon` (debug) or `just addon-release`; the napi CLI writes `unfold-node.<platform>.node`, `index.js`, and `index.d.ts` into the crate folder. `just addon-test` runs its Node tests against the build.

## Window commands that involve the engine

- **Add and remove projects.** `add_project` shows the folder picker, then sends the trusted `add_project` and returns `{status, project}` (`exists` when the folder or its repository already is a project), or null if the picker was cancelled. Remove Project asks first with `confirm_remove_project {name}` ("Remove <name> from the workspace? Its .unfold folder stays."); the UI then calls the engine's `remove_project`.
- **Export.** The UI calls `window.unfold.window("export_mermaid", {project, board, page, title})` (or `{project, entrance, title}`). The main process shows the save dialog (default name `<title>.mmd`, in Documents), then sends the trusted `export_mermaid` request for the calling window with the chosen path, and returns `{path, bytes}`, or null if the dialog was cancelled. Engine errors (`board_not_held`, `io`, …) reject with their code. `export_mermaid_text` stays an ordinary engine command, for copying. Share › Export PNG… calls `window.unfold.window("export_png", {project, board, page, title})`: the main process shows the save dialog (default name `<title>.png`, the UI passing `<board title> - <page title>`), has the [render window](#the-render-window) draw the page at scale 2, unsaved edits included, writes the PNG itself, and returns `{path, bytes}`, or null if the dialog was cancelled; a page that couldn't be drawn rejects with the reason (`render_timeout`, …).
- **Clipboard.** Windows get no permissions at all, so `navigator.clipboard.writeText` is denied (`NotAllowedError`, verified end to end). The UI copies with the window command `copy_to_clipboard {text}`, which the main process writes with Electron's `clipboard`. Copy Mermaid is `export_mermaid_text` followed by `copy_to_clipboard`.
- **Move to New Window.** `move_tab_to_new_window` opens a window and resolves with its id at once. The UI then calls `move_board {project, id, toWindow}` (the claim moves in Rust) and `window.unfold.window("transfer_board_state", {toWindow, payload})`; the target window receives `{type:"board_state_transferred", fromWindow, payload}` (held until its UI has loaded). Subscribe to it at startup.
- **Held boards.** When `open_board` answers `held` with `heldBy`, the UI calls `focus_window {windowId, board: {project, board}}`; that window receives `focus_board` and shows the tab.
- **Drag and drop.** Dropping a folder on a window adds it to the workspace. The preload records the paths of the latest drop (`webUtils.getPathForFile`) and only those can be added: `window.unfold.addDroppedFolder(file)` from a UI drop handler, or, if the UI doesn't handle the drop, the preload adds a single dropped folder by itself and emits `project_added` (or `project_add_failed` with the engine's reason). The engine checks the path is a folder (`not_a_folder` otherwise).
- **Undo and Redo.** Edit > Undo / Redo (and their shortcuts when the UI didn't handle the key) arrive as `menu_command` `undo` / `redo`. With focus in a text field, the preload runs the field's native undo instead and the UI sees nothing.

## The agent bridge

`src/main/agents/` is how the main process has windows act for an agent ([docs/ui-shell.md](../docs/ui-shell.md#agents-in-the-window) is the window's side; [U-54](../docs/decisions-and-tradeoffs.md#u-54-the-window-that-holds-a-board-applies-an-agents-edits)). The requests, answers, and view reports are typed in `src/shared/agent-api.ts`, which the UI imports as `@unfold/desktop/agent-api`. The MCP server's tools call it.

- **View reports** (`views.ts`). Each window sends `report_view {board?, page?, selection, lens?, visible, tabs}` when its view changes (debounced 150 ms) and when it gains focus. `ViewTracker` keeps the last report of each window (`parseViewReport` refuses malformed ones), the order windows were used in (from each window's `focus` event, `onFocused`), and which window holds a board (from the reported tabs, and at once when one opens it for an agent).
- **The bridge** (`bridge.ts`). `AgentBridge` routes each request to the window that holds the board, as a shell event delivered once the window's UI has loaded, and waits for the window's answer command (`agent_<request>_result`: `edit`, `read`, `open_board`, `create_board`, `edit_board`, `show`, or `repair`); an answer from another window, of another kind, or after the timeout is ignored, and one that isn't shaped right fails as `internal`.
  - `edit(input)`: makes sure a window holds the board (`open`), and with `expectRevision` reads the page first and refuses with `revision_mismatch` when it changed. Then the window applies the operations as one undo step and answers with the page as saved; the bridge adds the page's revision. A window that turns out not to hold a board its report listed (`board_not_open`) gets the board opened again, once.
  - `read({board, page})`: the page as the holding window has it, unsaved edits included, with its revision and the sizes the window's canvas measured; `board_not_open` when no window holds the board.
  - `open({board, page?})`: the holding window, else the window used last (else the first, else a new window) opens the board in a background tab; a board another window holds turns out to be that window's, and one held where no window can reach fails with `board_held_elsewhere`.
  - `create({project, title?, folder?, pages?, copyOf?})`: the window used last (else the first, else a new window) creates a draft and holds it in a background tab, so that window claims it; with `copyOf`, the window that holds that board copies it (`duplicate_board` needs the holder) and opens the copy in a background tab.
  - `editBoard({board, agent, title, ops, replacePeopleText?})`: like `edit`, for a board's pages (add, rename, move, duplicate, delete) and title, as one undo step in the holding window.
  - `show({board, page?, item?}, background)`: in the background, only `open`; otherwise the holding window switches to the tab and page, selects and centers the item (`agent_show`), and the registry brings that window to the front.
  - `repair({board, page, agent, repair, items})`: like `editBoard`, for one `repair_board` repair the holding window applies as Review does (its unsaved edits saved first, one undo step), outlining `items` as the agent's work; the answer gains the page's revision.
  - `finish({board, agent, summary})`: the holding window (else the window used last) clears the agent's working marks and shows the summary as a toast.
  - **The work log.** The bridge remembers the boards each agent edited or repaired (`workedOn(author)`) until it finishes its work on them, so `finish_work` finishes where the agent worked.
  - Every request times out after 30 s (`timeout`; `unconfirmed` for a change, which the window may still apply, since it can't be told to drop a request), and a window that closes first fails its requests with `window_closed`.
- **Page revisions** (`revision.ts`). `pageRevision(page)` is the first 8 hex digits of FNV-1a 64 over the page's JSON with sorted keys and a two-space indent, as UTF-8. Only the main process computes it.
- **Links** (`links.ts`, [U-63](../docs/decisions-and-tradeoffs.md#u-63-the-current-view-and-links-that-only-the-server-reads)). `parseLink` reads `unfold://<project's shared name>/<board id>?page=<page id>&item=<item id>` (each part URI-encoded; an item needs its page) and says why text isn't one; `resolveLink` names the project by id, the first in workspace order with the shared name.

## The render window

`src/main/agents/render.ts` draws pages for images (an agent's `get_screenshot`, and Share › Export PNG) and for the page checks (an agent's `check`) in a hidden render window ([design §5.1](../docs/proposals/agent-mcp-design.md#51-where-it-runs-and-why), [U-60](../docs/decisions-and-tradeoffs.md#u-60-page-images-from-a-hidden-render-window-and-page-checks)). The messages are typed in `src/shared/render-api.ts` (`@unfold/desktop/render-api`); the window's side is `ui/src/render/` ([docs/ui-shell.md](../docs/ui-shell.md#the-render-window)).

- **The window.** `PageRenderer` creates it on demand: a `BrowserWindow` with every window's hardening, offscreen (`offscreen: {deviceScaleFactor}`, so it never shows, can be larger than the screen, and draws at a fixed scale) and without background throttling, loading `app://unfold/render.html` (the dev server's `render.html` in development). It takes an engine window id from the registry's sequence (`reserveId`) and is attached to the engine host once its UI loads (again after an engine restart), for the cards' data; it never opens or claims a board. It may send one window command, `render_ready`, and no other window may send that. A request at the other scale (1 or 2) replaces it. It closes after a minute without a request, when it stops answering, and on quit.
- **One page at a time.** Requests queue. For each, the main process hands the window the page with `render_page {purpose, board, title, page, health, item?}`: the page as the window holding the board has it (`AgentBridge.read`, unsaved edits included) with the board's health (`board_health`, run for that window), or, when no window holds the board, as its file has it (`read_board`, no health, so no review banners). The window adopts it read-only, draws it with the board tab's canvas, waits until it has settled, and answers `render_ready` with the bounds to capture or the page checks.
- **Images** (`screenshot({board, page, item?, scale?})` → `{png, width, height, note?}`). From the bounds of the page or of one card, frame, resource card, or note, `imageFrame` picks the zoom (1 when it fits, else what keeps the long side at 4,096 pixels) and the window's size with 24 px of padding; the main process resizes the window, sends `render_frame {camera, width, height}`, and once the window answers, captures it (`capturePage`, PNG at the scale). The note says when the image was drawn smaller, or has no review banners.
- **Checks** (`check({board, page})`, `checkBoard({board})`): the page's health items with their repairs (`board_health`) and the page checks the window ran on the drawn page (`{kind, items, message, suggestion}`), for one page or every page in order. Health needs the board's session, so a board no window holds is opened in a background tab first, as for an edit.
- **Refusals** are `{ok: false, code, message}`: `board_not_found`, `page_not_found` (listing the pages), `empty_page`, `item_not_found`, `item_hidden` (inside a collapsed frame), `render_timeout` (30 s to draw a page, 15 s to frame it; the window is closed), `render_failed` (the window closed or crashed), `internal` (a malformed answer), and the bridge's and engine's codes as they are.

## The MCP server

`src/main/mcp/` is the server agents such as Claude Code and Codex connect to ([design §5](../docs/proposals/agent-mcp-design.md#5-how-agents-connect-one-local-mcp-server), [U-52](../docs/decisions-and-tradeoffs.md#u-52-one-mcp-server-in-the-main-process-on-a-fixed-local-port-with-no-token), [U-53](../docs/decisions-and-tradeoffs.md#u-53-the-mcp-sdks-v2-server-stateless-with-no-sessions)). It runs in the main process, because the app owns the open projects (their locks) and boards (one window each), and only while Preferences › Agents has it on.

- **Listener** (`listener.ts`). Node's HTTP server on `127.0.0.1:<port>` (`agents.port`, 29180 unless the person picks another), serving `/mcp` and nothing else (404). A request with an `Origin` header (a web page) or a `Host` other than `127.0.0.1:<port>` or `localhost:<port>` (DNS rebinding) is refused with a bare 403; a body over 1 MiB with 413, before anything parses it. The rest reaches the SDK as a web `Request`, its JSON parsed once, and the `Response` streams back. Turning agents off closes every connection. A port another program holds is reported (`port_taken`), never a crash.
- **Protocol** (`server.ts`). The official MCP TypeScript SDK (`@modelcontextprotocol/server`, bundled into `out/main` with zod) serves Streamable HTTP statelessly: a fresh server from one factory per request, on the current revision (2026-07-28: `server/discover`, each request carrying its client in `_meta`) and on earlier ones (the `initialize` handshake, served statelessly too). It offers tools, prompts, and the instructions (`instructions.ts`); no resources, sampling, roots, or logging.
- **Who calls** (`identity.ts`, D5). On the current revision each request's `clientInfo` names the agent; on earlier ones only `initialize` does, so the server remembers that name by `User-Agent`, falling back to the `User-Agent`'s product. Claude Code is `agent:claude`, Codex `agent:codex`, any other client `agent:<its name, lowercased>`, keeping only `a`–`z`, `0`–`9`, `.`, `_`, and `-`, at most 32 characters (`agent:unknown` when nothing is left). The agents seen since the server started (with when each last acted) feed Preferences › Agents through `agent_server_status` and the `agent_server_changed` shell event, sent at once when the server starts, stops, or fails, and at most once a second while agents act (`service.ts`).
- **Routing.** Tools reach the engine untrusted (`EngineHost.untrusted`, for no window, or as the window that holds a board for a command that needs the board's session: `board_health`, `export_mermaid_text`): a trusted-only command is refused as a window's would be, and there is no pass-through to the engine. Board reads and edits go through the agent bridge to the window that holds the board. The one exception is adding a project: the person confirms it in a native dialog ("Claude wants to add `~/repos/payments` to your workspace.", Cancel by default), and only then does the trusted `add_project` run.
- **Tools** (`tool.ts`, `tools/`). `defineTool({name, title, description, input, annotations, alwaysLoad?, run})`: `input` is a zod object the SDK checks before `run`; `description` is where the tool teaches (at most 2,048 characters, which a test enforces); `alwaysLoad` sets `_meta["anthropic/alwaysLoad"]`. `run(args, context)` gets a `ToolContext` (`context.ts`): the agent, the bridge and the views, the render window (`renderer`), `engine(command, args)` typed by the generated IPC types, `held(board, command, args)` for a command that needs the board's session (run as the window that holds it), `stream(command, args, onMessage)` for a streamed command, `projects()`, `project(id, name, or link)`, `link(text)`, `revision(page)`, `addProject(path)`, `header(place)`, and the call's abort signal. Results (`results.ts`) start with a header (`Unfold · ts-orders › Order placement (draft) › Placing an order · rev 1a2b3c4d · as Claude`), stay compact, page with `paged` and `nextLine` (`pagedLines` for lines, which also ends a page before the size guard would cut it; `cursorOffset` for lists a tool pages itself), and are cut at about 6,000 tokens; a `ToolError` (`cant(what, why, instead)`, carrying the engine's or window's `code` when it is theirs) becomes a refusal that teaches, and the engine's errors gain what to do next. Tools are listed in `tools/index.ts`; prompts (`definePrompt`) in `PROMPTS` there; `tools/testing.ts` runs a tool against a fake engine and window for tests.
- **What a tool works on** (`target.ts`). The ids or link the arguments give (a link in any of `board`, `page`, `item`, or `project` names the rest; plain ids override its page and item), else the board and page in view in the window used last (`resolveBoard`); a board id alone is found among the projects' boards, and two projects with that id ask for `project`. `projectOrView` is the project named, else the project of the board in view, else the workspace's only one; `codeTarget` is a key, a link to a card, or the card selected in view (a step's or step group's card, in the project its `ref.project` names). `readPage` reads a page from the holding window (unsaved edits included), else the board's file (`read_board`). Results name things with `format.ts`: Unfold's names for keys, `file:line`, written types with what each name links to, and line labels as the board draws them.
- **Set up and navigate** (`tools/setup.ts`, `tools/boards.ts`). `add_project` expands `~/`, asks the person, then reports what a first Compile would read (`compile_preview`). `compile_project` races `compile` with `waitSeconds` (at most 50) and the call's signal; past it, the compile goes on in Unfold and the result gives `project_summary`'s progress. `update_project_settings` sends the file's edits in one `update_project_config` (all or nothing), then `set_background_updates`, and returns the change to `.unfold/config.toml` as a line diff (`diff.ts`) of `project_config` before and the result after. `create_board` checks a `trace` entrance (`peek`) before anything is created, has the bridge create the draft, then traces it with an `add_cards` edit (`follow: {callees: 1}`, one undo step "<agent> · Trace"). `organize_boards` runs folder operations and `set_board_folder` in the engine, a rename as an `editBoard` and a copy as a `create` in the holding window, in order, saying what was done before a failure; agents never delete, publish, or discard a board, or move one back to drafts. `edit_pages` is one `editBoard`; `show` is the bridge's `show`.
- **Read the code** (`tools/search.ts`, `tools/code.ts`, `tools/calls.ts`, `tools/files.ts`). `search` runs one name search per kind (functions and types are definitions narrowed by `definitionKinds`, so each has its own total) and `search_text` through `stream`; a text hit's function is the innermost definition of `file_view`'s outline of that one line. `list_entrances` pages `entrances` per application. `read_code` reads `card` (both models), a type's `type_definition`, and a function's owned edges (`relations`, named) with their `line_labels`; it shows source, steps, and throws only when the file is the one compiled, in pages of at most 150 lines (fewer when they are long). `read_call` reads `call_contract` for a source and seq, or the line (or merged arrow) selected in view. `read_file` reads the whole `file_view` for the outline and shows a range of verified text (`current` or `evidence` only). `get_relations` pages `relations`' callers or `type_uses`, and lists `board_refs`.
- **Read and check boards** (`tools/pages.ts`, `tools/review.ts`). `list_boards` lists a project's boards (`list_boards`) with each listed board's pages from its file (`read_board`), whether it is open in Unfold or in view, and its health label, 30 at a time; with several projects and none named or in view, every project's drafts and unpublished changes (`drafts`). `read_page` reads the page through `readPage`, then each card's models (`card`) and the definition of each type card showing its fields (`type_definition`) (`page-code.ts`, which copies the canvas's rules for arrows and the outline's count of unlabeled steps), and lists every item with its id: cards (name, `file:line`, key, view, folded, frame, position and measured size, description and author), step groups (their lines), frames as a tree, resource cards, connections and drawn links (a step at `file:line` from its card's model), notes, the arrows the canvas draws (each call occurrence whose target has a card on the page, by the canvas's rules, with its `line_labels` label and the source and seq `read_call` takes; an entrance's handlers), type arrows (a field's declared names to other cards), and the Flow steps still unlabeled (cards shown in Flow, keyed steps without a page label, Start, End, and the steps a collapsed step group of the card hides aside), 120 lines a page (fewer when they are long); `format: "mermaid"` is `export_mermaid_text`, run as the holding window (`ToolContext.held`, which opens the board in a background tab when no window holds it). `check` and `get_screenshot` call the render window (`ToolContext.renderer`, the `PageRenderer`): `check` lists the page's (or, for a board named without a page, every page's) health items, each with the `repair` calls it offers, and the page checks with their suggestions; `get_screenshot` returns the PNG as MCP image content after a one-line header.
- **Build, shape, and explain** (`tools/build.ts`, `tools/shape.ts`, `edits.ts`). Each write tool is one agent edit of one page through `AgentBridge.edit`: `editTarget` finds the page (ids, a link, or the page in view; a board named without a page only when it has one page), `localIds` turns links in item arguments into ids of that page, projects become ids (absent for the board's own), `expectRevision` goes to the bridge, and `editResult` writes the header with the page's new revision, each item with its name, id, and status (`itemLine`: cards with where following stopped, step groups with the statements they took, frames with what they hold, connections with the channel the save filled in), the window's warnings, the ids, and a `Next:` hint. `add_cards`, `set_view`, `arrange_page`, `remove_items`, `group_steps`, `frame_cards`, `add_resources`, `connect`, `add_notes`, `describe`, and `label_steps` send the operation of the same name (`arrange` for `arrange_page`). Of these, only `remove_items`, `describe`, and `label_steps` take `replacePeopleText` (design §6.11; `edit_pages` takes it too, for deleting a page that holds a person's words); the others turn the window's advice to pass it into advice to keep the person's words.
- **Repair and finish** (`tools/finish.ts`, `health.ts`). `repair` reads the board's health as the holding window (`board_health`), finds the item on the page that offers the repair (an anchor's, when several anchors have problems), refuses to re-sign or accept what a person wrote (D6: a card's description, and for accept also its step groups and Flow labels; a step group's title and description; a label; a connection, resource card, or frame description and their texts), builds the `repair_board` request, and has the holding window apply it (`AgentBridge.repair`). `finish_work` finishes the board named, else every board in the bridge's work log for the agent, else the board in view, with `AgentBridge.finish`.
- **What the server teaches** ([design §7](../docs/proposals/agent-mcp-design.md#7-teaching-agents-to-draw-good-diagrams), [U-62](../docs/decisions-and-tradeoffs.md#u-62-teaching-through-instructions-a-guide-prompts-and-descriptions)). The teaching is product surface, kept beside the code it describes:
  - `instructions.ts`: what every session starts with. At most 2,048 characters (Claude Code's cut), and its first paragraph, at most 512 (what Codex reads first), says what Unfold is and ends with the call to read the `start` topic.
  - `guide/`: the eight topics `get_guide` returns, one Markdown file each, bundled as text (`?raw`): `start` (how Unfold works, the workflow, the diagram brief, ids and revisions, the review checkpoints, the rules, and which topic to read before which job), `diagrams`, `connections`, `data-models`, `graph`, `writing`, `setup`, and `repairs`. Examples come from `ts-orders` and the typed-lines fixture, and each topic fits one result.
  - Each tool's description (what matters first, the rules it enforces, the topic to read before it) and its results' and refusals' wording, in `tools/*.ts`, `results.ts`, and `format.ts`.
  - `tools/prompts.ts`: the six prompts (`explain-entrance`, `simplify-function`, `service-map`, `data-model`, `tour`, `fix-boards`), which Claude Code lists as `/unfold:<name>`. Claude Code splits what follows the command on whitespace, so each argument is one word (`explain-entrance` takes a route's method and path as two), and each may be left out for what the person is looking at.
  - `teaching.test.ts` checks the limits, that every name written like a tool's in the instructions, topics, prompts, and descriptions is a tool or a value a tool's arguments take (`OTHER_WORDS` lists the few that are neither), that every topic named exists, that every tool is taught somewhere, and that the prompts render with and without their arguments.
- **Tuning the teaching.** `src/main/mcp/tasks.md` is the task suite: tasks on `ts-orders`, `py-orders`, the mixed playground, and the typed-lines fixture, each with what a correct result contains and a rubric (facts, readability, effort, rules). Run them with Claude Code and Codex connected to a dev build, change one text at a time, and run them again.

## Window restore

[Architecture §11.10](../docs/architecture.md#1110-several-windows-and-restore). Every window has a stable `key` (`window_info().key`), and `windows.json` in app data remembers each one.

- At launch the main process asks the engine for the saved windows (trusted `saved_windows`) and recreates each with its key, bounds, and maximized state, moved onto the primary screen if no screen shows its title bar any more. At most 16 come back; with none, one new window opens. A folder from the command line, `open-file`, or a second launch joins the workspace, and the focused window receives `project_added` so it selects it, or `project_add_failed {path, message}` so it says why it couldn't be added.
- The main process saves a window's bounds (`save_window_bounds`) when it is created and after each move or resize (debounced 500 ms).
- The UI saves each window's selected project, tabs, and layout with `save_window_state {state: {key, …}}` and restores them with `window_state {key}`.
- A window the person closes is forgotten (`forget_window`) unless it was the last one. The last window, and every window open when the app quits, comes back.

## Packaging

`electron-builder.yml` packages the app ([architecture §14](../docs/architecture.md#14-packaging-platforms-and-updates)): a `.dmg` and `.zip` per Mac architecture, an NSIS installer for Windows x64, and an AppImage, `.deb`, and `.rpm` for Linux x64. `just bundle` builds this platform's installers into `dist/`, `just bundle-dir` only the unpacked app.

- **What ships.** The archive holds `package.json`, `out/` (main, engine host, and preload, bundled by electron-vite with electron-updater and the MCP SDK inside), and `ui/` (the Vite build), without source maps or `node_modules`. The addon (`index.js`, `package.json`, and this platform's `.node` file) sits outside the archive at `<resources>/unfold-node`, next to `THIRD_PARTY_NOTICES.md` (and, on macOS, Electron's `LICENSE.electron.txt` and `LICENSES.chromium.html`).
- **Fuses.** Set at package time ([§13](../docs/architecture.md#13-security-and-privacy)): RunAsNode, NODE_OPTIONS, and the inspector off; cookie encryption, asar integrity validation, and loading only from the asar on; no extra `file://` privileges. Flipping fuses voids the Electron binary's signature, so an unsigned macOS build is re-signed ad hoc.
- **Signing.** Only from the environment (`CSC_LINK` / `WIN_CSC_LINK` and their passwords; notarization from `APPLE_API_KEY*`). `just bundle` never uses an identity it merely finds in the keychain, so local builds are unsigned unless you pass one. The hardened runtime's only entitlement is JIT (`build/entitlements.mac.plist`).
- **Updates.** `updater.ts` checks GitHub Releases half a minute after launch and every six hours, if the `updates.enabled` preference allows it. Downloads must match the manifest's SHA-512; macOS and Windows install only updates signed like the running app (on Windows, by a publisher named in `app-update.yml`); the AppImage replaces itself; `.deb` and `.rpm` installs get a notice linking to the release. Updates are off in development and in any build the release workflow didn't make (it sets `unfoldReleaseBuild` in the packaged `package.json`).
- **Placeholders** (U-3): the app ID `dev.unfold.app`, the release feed `unfold-placeholder/unfold` (also `RELEASES_URL` in `update-policy.ts`), the Windows publisher name, and the Linux maintainer.
- **Smoke test.** `scripts/smoke.mts` (`just smoke`) runs against the unpacked app: it reads the fuses back from the binary; launches the app with an empty `PATH`, a throwaway home, and `ELECTRON_RUN_AS_NODE`, `NODE_OPTIONS`, and `--inspect` (all ignored); attaches Playwright over the DevTools protocol; adds a copy of the TypeScript playground in a path with spaces and non-ASCII letters as a project and compiles it; waits for the project to be current; checks the window from the inside (no Node globals, only `window.unfold`, inline scripts and the network blocked); and checks that nothing outside `.unfold/` changed and no planted execution sentinel ran. Every window's `webPreferences` are read from the main process of a copy of the app with the inspector fuse turned back on, because Playwright's Electron driver needs the inspector.
- **Icon.** `build/icon.svg` is a placeholder; `pnpm --filter @unfold/desktop exec electron ../tools/icons/render-icon.mjs` renders `build/icon.png`, from which electron-builder makes each platform's icons.

## Running

From the repository root:

```sh
pnpm install          # or: just js-install
just addon            # builds the engine addon (debug) into crates/unfold-node
just dev              # builds the addon, then the Vite dev server for the UI + electron-vite, with hot reload
just js-build         # builds ui/dist and desktop/out
pnpm --filter @unfold/desktop start   # runs the built app (loads ui/dist via app://)
just js-check         # typecheck, lint, and unit tests
```

Pass a folder to add it to the workspace: `pnpm --filter @unfold/desktop start -- /path/to/repo`.
